# Platform Event Bus

A generic, in-process publish/subscribe mechanism so engines communicate
through published events instead of depending on each other directly. This
milestone builds the bus itself and demonstrates real publication from the
three existing engines -- it does not build URP or the Webhook Engine, both
of which depend on this existing first.

## Why this exists

The Engine Framework (`lib/engine/`) already reserved a place for this:
`EngineMetadata.supportedEvents` has existed since that milestone as
"event names this engine would publish or react to once an Event Bus
exists." This module is that Event Bus. The Engine Framework itself
(`lib/engine/base.ts`, `types.ts`, `registry.ts`) is unmodified -- this is a
new, independent module the framework's engines now use, not a design
change to the framework's contract.

## The event model

Every published event carries standardized metadata (`EventMetadata` in
`lib/events/types.ts`) plus a strongly-typed payload:

| Field | Meaning |
|---|---|
| `eventId` | Unique id, generated by the bus |
| `eventName` | e.g. `'engine.health-checked'` |
| `eventType` | Coarse category; defaults to `'domain-event'` |
| `sourceEngine` | The publishing engine's id |
| `timestamp` | ISO 8601, generated by the bus |
| `correlationId` | Ties related events together; defaults to the event's own `eventId` when not supplied |
| `version` | Event schema version; defaults to `'1.0.0'` |
| `payload` | Strongly typed via `PlatformEvent<TPayload>`'s generic |
| `metadata` | Optional free-form extra context, separate from the standardized fields above |

## Capabilities

`EventBus` (`lib/events/bus.ts`) implements:

- **Publishing** -- `publish(input)`, async, returns a `PublishResult`
  (the full event, delivery count, per-subscription failures, and an
  overall status: `delivered` / `partial-failure` / `failed` /
  `no-subscribers`).
- **Subscription** -- `subscribe(eventName, handler, filter?)` returns an
  unsubscribe function; `eventName: '*'` subscribes to every event.
- **Multiple subscribers** -- every matching subscription is invoked per
  publish; one subscriber's failure doesn't affect another's delivery.
- **Filtering** -- narrow a subscription further by `sourceEngine` and/or
  `eventType`.
- **Error isolation** -- each handler runs in its own try/catch; a thrown
  error or rejected promise is recorded in `PublishResult.failed` and never
  propagates to the publisher or to other subscribers.
- **Validation** -- `publish()` rejects an empty `eventName` or
  `sourceEngine`.
- **Diagnostics** -- `getDiagnostics()` returns total published count,
  active subscription count, and a bounded (200 entries), most-recent-first
  event log -- what the Event Monitor Admin Console page renders.

Framework-agnostic and engine-agnostic by construction: `lib/events/`
imports nothing from `lib/engine/` or any specific engine, and nothing
here hardcodes an event name, engine id, or event type. `EventBus` is a
class (not a module-level singleton like `lib/engine/registry.ts`) so
tests can construct isolated buses; `eventBus` is the one shared instance
production code uses.

**Async by design, not by accretion:** `publish()` is already `async` and
handlers may return a `Promise`, so today's sequential per-subscriber
dispatch can move to a queue or worker later without any change to
`EventBus`'s public methods or their signatures.

## Engine integration

Each of the three existing engines (`lib/itcRecovery/engine.ts`,
`lib/vendorInvoices/engine.ts`, `lib/control-center/engine.ts`) publishes
one real event -- `engine.health-checked` -- from inside its existing
`getHealth()` method, immediately before returning the same `EngineHealth`
value it always computed. No business logic changed: the reconciliation,
invoice lifecycle, and commercial administration code these engines wrap is
untouched, and `getHealth()`'s return value is identical to before this
milestone. The only addition is the side-effect publish call, and the
`'engine.health-checked'` entry now populated in each engine's previously
empty `metadata.supportedEvents`.

```ts
async getHealth(): Promise<EngineHealth> {
  const configured = getAuthCapabilities(process.env).supabase;
  const health: EngineHealth = { status: configured ? 'healthy' : 'unhealthy', ... };
  await eventBus.publish({
    eventName: 'engine.health-checked',
    sourceEngine: this.metadata.id,
    payload: { status: this.getStatus(), health },
  });
  return health;
}
```

This was chosen as the integration point because it's the one place every
engine already does the same thing for the same reason (the Engine
Registry and `bootstrap.test.ts` both call `getHealth()`), so publishing
from it demonstrates cross-engine event flow without inventing a new call
site or touching real business logic anywhere else.

## Admin Console

`app/control-center/events/page.tsx` -- the reserved "Event Monitor"
placeholder, now implemented read-only. It runs a health check across
every registered engine (producing fresh `engine.health-checked` events)
and then renders the bus's recent event log: Event Name, Source Engine,
Timestamp, Status, Correlation ID. No replay or queue management in this
milestone.

## What's deliberately not here

Per this milestone's explicit scope: no Universal Report Platform, no
Webhook Engine, no persistent event store, no replay, no queue/worker
dispatch, no cross-process delivery (this is a single in-process bus, reset
on cold start same as the Engine Registry). The platform architecture
review's roadmap explains why URP and the Webhook Engine build on top of
this rather than alongside it.
